🚧 Path-scoped rules

📁 Why folders become borders

On Unix systems, file permissions are the oldest and most trusted ACL in computing. In the agentic era, the same principle applies:the folder structure is the first line of agent access control. When you define that "in /clinical/* apply rule X" and "in /billing/* apply rule Y", you are using the filesystem as an enforcement mechanism — not as a convention, but as an architecture.

🏗️Filesystem as ACL

  • •Physical borders— separate folders = separate domains. It's not soft policy.
  • •CLAUDE.md site— each folder can have its own rules file.
  • •Settings.json— allowlist/denylist by path pattern (glob syntax).
  • •Rules in the root CLAUDE.md— "NEVER read /secrets/", "ONLY edit /src/*".

💡Fundamental principle

Security by architecture is more robust than security by instruction. "Never read /secrets/" in CLAUDE.md is more fragile than a filesystem permission that physically prevents access. Use both layers.

2

🩺 Case of Dr. Sana

Dr. Sana is a dermatologist with her own clinic. It uses agents for clinical and administrative support. The challenge: clinical data (PHI — Protected Health Information) and administrative data (billing, scheduling) need to be treated in radically different ways.The solution was path scoping: two domains, two agents, one controlled bridge.

Architecture of Dr. Sana's clinic

  • /data/clinical/— medical records, diagnoses, exams. PHI. Clinical agent just reads. Zero writing without confirmation.
  • /data/billing/— invoices, insurance, payments. Admin. Billing agent has full access here.
  • /data/clinical/CLAUDE.md— "NEVER export data from this folder. Never send by email. Log every reading."
  • /data/billing/CLAUDE.md— "NEVER access /data/clinical/. Only use anonymized IDs for cross-referencing."
  • Controlled bridge— audited script that extracts minimum required data, with log and approval.

⚠️No path scoping — the risk

Without explicit boundaries, the billing agent could, in some task context, end up reading patient records to "better understand the context". HIPAA does not accept “it was by accident”. The penalty starts at $100 per leaked record.

3

📂 Folder structure for scope

The folder convention isn't decoration — it's thephysical basis of the scope. When all teams agree that /data/<domain>/ means "data from that specific domain", path scoping works. When folders are named randomly, the scope has nowhere to stand. Convention is half the security.

Recommended minimum convention

  • /data/<domínio>/— data by business area (clinical, billing, marketing).
  • /resumos/<área>/— Silver Platters and context by domain.
  • /agentes/<nome>/— CLAUDE.md and configuration of each specialized agent.
  • /skills/— slash commands shared between agents.
  • /logs/— audit trail, sessions, decisions. Read-only for agents.
  • /secrets/— never accessible by agent. Filesystem permission.

Sally — legal office

Sally separated /cases/<cliente>/ by client. The legal research agent only has access to /cases/cliente-active/ of the current session. Never sees other clients' cases. Attorney-client privilege preserved by architecture.

4

🚫 Ban rules by path

The allow lists and deny lists in CLAUDE.md and settings.json are the declarative path scoping mechanism. You specify exactly what the agenthe cando and what hecan neverdo, with folder, file and operation granularity. It's simple to write and powerful in practice.

Examples of rules per path

  • NEVER read /secrets/
  • NEVER write outside /src/ without approval
  • ONLY edit files matching /docs/**/*.md
  • NEVER delete files in /data/
  • ALWAYS log reads from /data/clinical/
  • NEVER send contents of /data/* externally

In settings.json

Use the keypermissionswith global standards. Ex:"Read(data/clinical/*)"in the deny list blocks reading in this path.

On CLAUDE.md

Natural language rules in the "Non-Negotiable Rules" section. The agent reads and applies it. More flexible, less harsh enforcement.

5

🛂 CLAUDE.md by subfolder

The most powerful feature of path scoping is placing a CLAUDE.md inside a specific subfolder. This file is readjustwhen the agent is working within that folder — that is, the rules are automatically activated by the location context.Granular override without inflating the root CLAUDE.md.

How it works in practice

  • /project/CLAUDE.md— general project rules. Always active.
  • /projeto/data/clinical/CLAUDE.md— active only when working in /data/clinical/.
  • /projeto/src/api/CLAUDE.md— active only when editing API code.
  • Domain specific rulesthey are in the CLAUDE.md subfolder; do not pollute the root.

💡Recommended standard — Dr. Sana

Dr. Sana's /data/clinical/CLAUDE.md contains: "You are working with PHI. All readings must be logged. Never copy data out of this folder. Never mention a patient's name in unaudited conversations." These 4 rules only exist in this folder — they do not affect other sessions.

6

✅ Cross validation

Isolated domains sometimes need to communicate — it's inevitable. Dr. Sana's billing needs to know if a procedure was performed to bill. The solution is not to open the domains, but to create acontrolled bridge: an explicit, audited, human-approved process that allows for the minimum necessary crossover.

Controlled bridge architecture

  • 1. Identify the minimum necessary— which data exactly needs to be crossed? Just ID + status?
  • 2. Audited extraction script— revised code that extracts only what is necessary, without raw PHI.
  • 3. Human approval— crossover hook requires explicit confirmation.
  • 4. Immutable Log— record of who authorized, when, what data was crossed.
  • 5. Anonymized data— the billing side receives internal ID, not name or record.

⚠️Anti-pattern

Create a "super-admin" agent with access to all domains to "facilitate" crossover. This agent is the most critical point of failure in the system. If compromised, all domains are leaked. Punctuality compensates for bridge overhead.
