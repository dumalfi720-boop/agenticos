🔐 Agent Permissions and Jurisdiction

🔓Permission modes

Claude Code operates in different permission modes that determine the level of agent autonomy in each session. Understanding these modes is fundamental to calibrating the balance betweenspeed and control. Too restrictive mode paralyzes productivity; Too open mode creates real risks.

The 4 main modes

  • Confirm (default)— every write, execute or delete action asks for confirmation. Maximum control.
  • Self-accept— actions pre-approved in the allowlist run without confirmation. Productivity/control balance.
  • Plan mode— agent plans and lists all actions before executing any. Good for complex tasks.
  • Bypass (--dangerously-skip-permissions)— without any confirmation. Only in controlled CI/CD pipelines.

💡Milestone — practical strategy

Marco uses confirm for new tasks and auto-accept for routine operations (npm install, reading docs, editing in /src/). Plan mode for deployments and schema changes. Bypass never in local development — only in the GitHub Actions CI.

2

⚙️ Allowlist and denylist

The settings.json is Claude Code's central permissions configuration file. With it, you define whichBash tools and commandsthe agent can execute without asking for confirmation — the allowlist — and which are explicitly prohibited — the denylist. The granularity is impressive: you can releasenpm run testbut prohibitnpm publish.

Configuration examples

  • // Allowlist — runs without confirmation
  • "Bash(npm run test)", "Bash(npm run lint)"
  • "Read(src/**)", "Edit(src/**)", "Edit(docs/**)"
  • // Denylist — never runs
  • "Bash(npm publish)", "Bash(git push --force)"
  • "Bash(rm -rf *)", "Edit(/secrets/**)"

Ergonomics vs safety

The purpose of the allowlist is to reduce friction for safe and repeatable operations. It's not about giving unlimited freedom — it's about not asking for confirmation for things you already know are safe. The denylist is absolute: these actions never happen, regardless of the context.

🌐Agent Jurisdiction

Each specialized agent has aterritory— the set of resources that he is authorized to access and modify. CFO Bot plays /finance/. CMO Bot plays /marketing/. Researcher Bot reads everything but writes only to /research/. This separation is not just about organization — it is the formal definition of jurisdiction that determines the radius of impact of each agent.

Jurisdiction by specialty — Framework

  • Product Bot— read/write /products/, /catalog/. It never touches /orders/ or /payments/.
  • Order Bot— read/write /orders/. Reads (only) /products/. Never accesses /customers/ PII.
  • Analytics Bot— reads everything in read-only mode. Writes only to /reports/.
  • Support Bot— reads /orders/, /customers/ (with PII). Never modify orders without approval.
  • Dev Bot— full access to /src/, /tests/. Zero access to production /data/.

💡Jurisdiction as contract

Jurisdiction is not just restriction — it is also clarity. When CFO Bot knows its territory is /finance/, it can operate with complete confidence in that domain. And you know exactly what can go wrong. Clear jurisdiction = predictable blast radius.

4

🤚 Human approval required

The concept of "jagged intelligence" (Brynjolfsson & McAfee) describes how AI is brilliant at many things and surprisingly weak at others — and you don't know where the hole is until you fall in.For high-impact or irreversible actions, human approval is not optional. It's the only way to ensure that errors are detected before they become catastrophes.

🚨Actions that always need approval

  • •Payments and transfers— any value above the defined threshold.
  • •Irreversible deletions— files, bank records, production assets.
  • •External communications— emails to customers, social media posts, webhooks.
  • •Force pushes and merges in main— direct changes in production.
  • •Permission changes— changes to settings.json or CLAUDE.md itself.

Practical implementation

Configure hooks in settings.json that intercept high-risk actions and require a specific confirmation string before proceeding. The agent can prepare everything, but execution only happens after the human types "CONFIRM: [specific action]".

🚪 Sandboxing

Sandboxing is the technique of isolating the agent in a controlled environment where errors are contained and rollback is trivial. In the context of Claude Code, the main sandbox strategies aregit worktrees(work isolated branch), Docker containers and ephemeral staging environments. In all cases, the principle is the same: agent operates on a copy, not on the original.

Sandbox Strategies

  • Git worktree— agent works in separate branch. Main is not affected until the PR is passed.
  • Docker container— isolated environment with access only to what you have assembled. Disposable.
  • Staging environment— agent operates in a test environment with anonymized data.
  • Read-only mounts— production data mounted as read-only; agent reads but does not write.

💡Worktree as default sandbox

For development, git worktree is the simplest form of sandboxing. The agent creates a branch, works on it, you review the diff and merge if approved. If something goes wrong, you delete the branch. Zero impact on production. The skillsuperpowers:using-git-worktreesautomates this flow.

📜 Principle of least privilege

O least privilegeis the oldest and most trusted security principle: every agent starts without any permissions, and you release only what is strictly necessary for the task. It's the opposite of "I'll give everything and then restrict" — which in practice never happens. Starting narrow and opening gradually is safer, more traceable, and easier to audit.

✗ Common anti-pattern

  • ✗Give full permission at the beginning to "make it easier"
  • ✗Never review permissions after it "worked"
  • ✗One agent with access to all systems
  • ✗Bypass mode as a development standard

✓ Correct pattern

  • ✓Starts with deny-by-default
  • ✓Releases permission when the task requires it
  • ✓Revoke after task completed
  • ✓Audit permissions periodically

Gradual unlock — the correct process

1. Identify exactly what the task needs. 2. Add only this permission to the allowlist. 3. Run. 4. If everything went well, keep going. 5. Quarterly, review accumulated permissions and remove what is no longer used. Unused permissions are risk without benefit.
