🧠 Why filesystem is the right metaphor

Agent memory is not a flat list of facts. It is a system withhierarchy, access paths, permissions and expiration— exactly like a file system. The metaphor is not poetic: it is functional. Organizing memory as a filesystem solves the problems that "list of facts" doesn't solve.

🗂️Properties that filesystem offers

  • •Hierarchy— /global, /project, /session. Different levels of persistence and scope.
  • •Access paths— the agent knows exactly where to look: /memoria/clientes/marco.md.
  • •ACL (permissions)— who can read, who can write, who can delete each memory.
  • •TTL— file expires in X days. Operating system cleans automatically.
  • •Namespace— memories from different projects do not contaminate each other.

💡Where does it appear today

Claude Code already implements memory as a filesystem:~/.claude/CLAUDE.md(global),projeto/CLAUDE.md(project),subpasta/CLAUDE.md(location). It's literally a hierarchical filesystem.

🪣 Letta/MemGPT — RAM vs Disk

The work of Charles Packer and team at UC Berkeley (MemGPT, 2023 → Letta, 2024) is the most rigorous academic implementation of structured memory for agents. The central idea:agents need layered memory, just like computers have RAM and disk.

🏗️The 3 layers of MemGPT

🟢 Core Memory (RAM = in-context)

Always present in the context window. Critical information that the agent needs at each turn: identity, rules, current task context.

Equivalent: CLAUDE.md active in the session. Size: small (~2-5K tokens).

🟡 Archival Memory (Disk = indexed)

Persistent and indexed memory. The agent searches it via query when needed. It can grow indefinitely — it doesn't stay in the context window.

Equivalent: Silver Platters, wikis, documents. The agent does "archival_memory_search('Black Friday campaign')".

🔵 Recall Memory (Cache = history)

Log of previous conversations. The agent looks for what was said/decided before, without keeping everything out of the window.

Equivalent: indexed session history. Query: "What did we agree about delivery last week?"

📒 Claude Code — memory on 3 levels

Claude Code implements hierarchical memory via native file system: three levels of CLAUDE.md withinheritance cascade. Global → project → local. Each level overwrites (or complements) the previous one for the scope it is in.

📁The CLAUDE.md hierarchy

~/.claude/CLAUDE.md          # Global: preferências do usuário,
                              # estilo de comunicação, ferramentas padrão.
                              # Vale para TODOS os projetos.

/projetos/meu-projeto/CLAUDE.md   # Projeto: stack, arquitetura,
                                   # convenções de código, personas.
                                   # Vale para este projeto.

/projetos/meu-projeto/frontend/CLAUDE.md  # Local: regras específicas
                                           # do módulo frontend.
                                           # Sobrescreve projeto para esta pasta.

📊What to put on each level

  • Global (~/.claude/CLAUDE.md)— tone of communication, language, preferred tools, rules that never change.
  • Project (project/CLAUDE.md)— architecture, stack, persona names, where the platters are located, team conventions.
  • Location (subfolder/CLAUDE.md)— module-specific rules: "this code uses TypeScript strict, never any", "tests are in /__tests__".

📖 Karpathy LLM Wiki — enriching memory

Andrej Karpathy proposed that agents should maintain aIncremental Markdown wiki— not a snapshot, but a knowledge graph that grows with each new observation. Entities, contradictions, syntheses and cross-links. It's the future of long-term memory.

📖LLM Wiki Structure

wiki/
  pessoas/
    cliente-marcos-antunes.md   # Histórico, preferências, decisões
    fornecedor-xyz.md
  projetos/
    campanha-black-friday.md    # Timeline, aprendizados, cross-links
    projeto-alpha.md
  conceitos/
    politica-desconto.md        # Regra da empresa + exceções registradas
  contradictions.md             # Log de conflitos e como foram resolvidos

💡How the agent writes on the wiki

After each relevant session, the agent executes a "memory synthesis" hook:

  1. Identifies new entities mentioned in the session.
  2. Checks whether pages for these entities already exist.
  3. Update or create pages with new information.
  4. Register contradictions with previous information at contradictions.md.
  5. Adds cross-links between related pages.

🔍Vector Stores and RAG

When memory grows beyond hundreds of files, keyword searching is not enough.Vector storesthey store embeddings — numerical representations of meaning — and allow semantic search: “what do we talk about loyalty discounting?” returns relevant documents even without the exact words.

🔍When to use RAG

  • •Memory < 100 files— hierarchical filesystem with enough grep. No need for vector store.
  • •100-10K files— hybrid search: FTS5 (text) + embeddings for semantic queries.
  • •10K+ files— Full RAG required. Tools: pgvector, Chroma, Qdrant, Pinecone.

📊RAG in practice for each persona

  • March— portfolio of 500 customers: RAG to search purchase history by semantics.
  • Sally— jurisprudential base with 10K decisions: RAG essential for searching for legal concepts.
  • Sana— internal medical literature + clinical cases: RAG to search for differential diagnosis.

⏳ TTL, Scope and ACLs

Memory without expiration policy and access controlbecomes pollution. The agent trusts obsolete data, leaks information between projects or accidentally overwrites critical memory. TTL, scope and ACL are memory governance.

⚙️The 3 dimensions of governance

⏰ TTL (Time to Live)

Each memory item has a declared validity. After expiring, the item is marked as stale or deleted.

# No frontmatter do arquivo de memória
---
ttl: 30d        # Expira em 30 dias
created: 2026-05-01
owner: agente-cmo
---

🗂️ Scope (Namespace)

Memory from one project does not leak to another. Scope ensures isolation.

memoria/
  global/       # Todos os projetos
  projeto-a/    # Isolado: apenas projeto A
  projeto-b/    # Isolado: apenas projeto B

🔐 ACL (Access Control)

Who reads, who writes, who deletes each memory. Especially critical for sensitive data (medical, legal, financial).

# Permissions
read: [agente-cmo, orquestrador]
write: [agente-cmo]
delete: [admin]

✓ Well-governed memory

  • ✓TTL declared in each file
  • ✓Namespace per project/client
  • ✓Explicit ACL for sensitive data
  • ✓Human curator reviews monthly memory

✗ Memory like swamp

  • ✗No TTL — everything stays forever
  • ✗Single namespace — projects cross-contaminate each other
  • ✗No control of who wrote what
  • ✗Unisolated medical/legal data
