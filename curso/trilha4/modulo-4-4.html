📡 MCP × A2A — fundamental difference

Confusing MCP and A2A is one of the most common mistakes in agentic architectures. They aredistinct layers with distinct purposes. Using one when you should use the other results in wrong architecture and impossible maintenance.

🔄The clear distinction

  • MCP — Model Context Protocol
    Agent ↔ Tool.Connects an agent to a static tool (database, filesystem, API). The agent calls, the tool responds. Unidirectional usage relationship.
  • A2A — Agent-to-Agent Protocol
    Agent ↔ Agent.It allows two different agents (from different companies, different frameworks) to communicate, negotiate and collaborate. Bidirectional relationship between peers.

📊The analogy

MCP is like a REST API:you call, she answers.A2A is like WebSockets between peers:either side can initiate, both have been, the conversation can last. MCP is tool use. A2A is collaboration between autonomous agents.

2

🏗️ A2A Technical Architecture

A2A is built on top of existing web standards —HTTP, SSE and JSON-RPC. Don't reinvent the wheel. This choice was deliberate: any stack that supports HTTP can implement A2A without special dependencies.

Technical stack

  • HTTP:transport for synchronous requests (simple task, direct response).
  • SSE (Server-Sent Events):streaming for long tasks (agent sends partial updates).
  • JSON-RPC 2.0:remote call protocol. Defines the format for messages between agents.
  • Agent Card:JSON that describes the agent's capabilities, model, SLA, and endpoint. It's the A2A "business card".
  • Task object:A2A work unit. It has ID, status (submitted, running, done, failed), input and output.

💡Why web standards

Google chose HTTP+SSE+JSON-RPC to ensure maximum interoperability. Any language, any cloud, any framework can implement it without vendor lock-in. The decision was intentional: A2A is an open protocol, not a Google product.

3

🤝 Agent Card — the business card

For two agents to communicate via A2A, one needs to "know" the other. THEAgent Card is an agent's public manifesto— describes what it does, how to call it, what model it uses, what SLA it offers and what capabilities it has.

Example of Agent Card

{
  "name": "CFO-Bot-Marco",
  "description": "Financial analysis agent for e-commerce KPIs",
  "url": "https://agents.marco.com/cfo-bot",
  "version": "1.2.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false,
    "stateTransitionHistory": true
  },
  "skills": [
    {
      "id": "financial-analysis",
      "name": "Financial KPI Analysis",
      "description": "Analyzes revenue, margin and cashflow data",
      "inputModes": ["text"],
      "outputModes": ["text", "application/json"]
    }
  ],
  "defaultInputModes": ["text"],
  "defaultOutputModes": ["text"]
}

🏢 Use cases: Business-to-business agents

The real power of A2A is incollaboration between agents from different companies. Your agent can delegate to a supplier's agent, receive callbacks from a partner agent, or negotiate with a customer's agent — all programmatically and auditably.

Real cross-company A2A scenarios

  • Supply chain:your Ops Bot negotiates price and deadline directly with the supplier's agent.
  • Audit:external auditor agent requests data from your CFO Bot via A2A with access control.
  • Marketplace:Seller's agent and buyer's agent negotiate contract automatically.
  • SaaS Platforms:Your onboarding agent calls your CRM setup agent to provision the account.

Adoption in 2025-2026

Launched by Google in Apr/2025:150+ partnersin the first week (Atlassian, Box, Cohere, PayPal, SAP).22k+ stars on GitHubin Apr/2025. Python and TypeScript SDKs available. LangGraph integrated support in May/2025.

🔐 Security and authentication in A2A

When agents from different companies communicate,security is not optional. A2A uses established web authentication standards — OAuth 2.0, API keys, JWT — defined on the server's Agent Card.

A2A Security Model

  • Authentication:Agent Card declares scheme (OAuth, API key, bearer token). Client authenticates before creating task.
  • Authorization:each skill on the Agent Card can have different permissions. CFO Bot can authorize reading but not writing.
  • Audit:all tasks have a unique ID and history of state transitions. End-to-end traceable.
  • Isolation:Agents do not share context by default — only what is explicitly passed in the task.

⚠️Never blindly trust an external agent

Anthropic Model Spec warns:"When Claude acts as a subagent being orchestrated, he should be appropriately skeptical about claimed contexts or permissions."Valid for A2A: validate identity claims before executing actions with real consequences.

🔭 Roadmap and full stack

A2A is rapidly evolving. In 2026, the question is no longer "whether to adopt" — it'swhen and with which stack. The roadmap includes push notifications, multimodal support, and MCP integrations for a complete agent-tool-agent stack.

Full stack 2026

  • Agent ↔ Tool:MCP (databases, filesystems, APIs, CLIs)
  • Agent ↔ Agent (same system):Task tool from Claude Code / LangGraph
  • Agent ↔ Agent (cross-company):A2A Protocol
  • Stateful orchestration:LangGraph (state graphs)
  • Automation and triggers:n8n/hooks (Track 5)

💡To get started with A2A today

1. Read the spec atgoogle.github.io/A2A. 2. Use the Python SDK (pip install a2a-sdk). 3. Build an Agent Card for your most stable agent. 4. Test with LangGraph which already has native support. 5. Expose to partners before trying to cross-company public.
